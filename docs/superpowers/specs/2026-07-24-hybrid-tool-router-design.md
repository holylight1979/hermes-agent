# Hermes 混合式前置工具路由器設計

日期：2026-07-24
狀態：已核准設計，待使用者審閱規格

## 1. 目標

在不犧牲工具可達性、安全核准與提示快取的前提下，讓 Hermes 對每則使用者訊息全自動判斷所需能力，只向主模型提供少量常駐工具與本輪必要的精簡工具資訊，降低輸入 Token、工具選擇負擔與端到端延遲。

第一版同時套用 CLI 與所有 Gateway 平台，使用相同核心實作與設定。路由錯誤或路由服務故障時必須失效開放（fail open）：全部原本獲授權的工具仍可透過橋接器找到並呼叫，但不得因此繞過工具組範圍、核准、安全掛鉤或輸出截斷。

## 2. 非目標

- 不把 rdchat-direct 升格為安全、權限或架構決策者。
- 不改變 Hermes 主模型。
- 不降低壓縮門檻。
- 不弱化命令核准、退縮 ERROR、安全掛鉤或工具組限制。
- 不在每輪直接增減模型 API 的 `tools` 陣列。
- 不要求使用者手動選擇快速／完整模式。
- 不以第一版解決技能全文、記憶全文或一般對話歷史的所有 Token 成本。

## 3. 現況與根因

現有 `tools/tool_search.py` 已提供 `tool_search`、`tool_describe`、`tool_call` 三個橋接工具，並確保間接呼叫仍經過 `model_tools.handle_function_call`、核准、外掛前後掛鉤、工具結果截斷與工作階段工具組範圍檢查。

目前阻礙是 `_HERMES_CORE_TOOLS` 同時承擔兩種不同語意：

1. 平台預設擁有的完整能力集合。
2. 工具搜尋永遠不可延遲的集合。

因此終端機、檔案、瀏覽器、排程、子代理、工作階段搜尋、記憶等大型結構全部常駐。這個耦合必須拆開：平台能力不等於模型每輪必須直接看見完整參數結構。

## 4. 選定方案

採用「混合式前置路由＋固定橋接器」。

### 4.1 固定模型工具面

同一工作階段中的模型 API `tools` 陣列固定，只包含：

- `clarify`
- `skill_view`
- `tool_search`
- `tool_describe`
- `tool_call`

若其中某工具不在當前工作階段原始授權範圍，則不得因常駐清單而新增權限。橋接器只能搜尋與呼叫該工作階段原本已授權且可用性檢查通過的工具。

### 4.2 混合式前置路由

每則新使用者訊息進入主模型前執行：

1. 零模型成本規則判斷明確情況。
2. 規則信心不足時，呼叫 `rdchat-direct/gemma4:e4b-64k` 做嚴格 JSON 分類。
3. 依分類結果，從工作階段授權工具目錄選出少量候選工具。
4. 產生有大小上限的本輪路由封包，附於當輪訊息尾端，而不修改固定的 `tools` 陣列。

路由封包包含：

- 判斷來源：`rule`、`ai` 或 `fallback`
- 能力類別
- 候選工具名稱
- 候選工具的一句說明
- 必要時提供精簡參數結構
- 明確告知主模型：若候選不足，使用 `tool_search`

候選工具結構只存在於本輪可變尾端，不改變長期提示前綴，因此保留主要提示快取。

### 4.3 快速規則

第一版規則只處理高信心案例，避免建立脆弱的大型關鍵字系統：

- 純社交／短確認且無外部事實需求：無候選工具。
- 明確網址、最新資訊、天氣、新聞、版本：網路能力。
- 明確檔案路徑、程式碼、測試、建置、命令：檔案與終端機能力。
- 明確瀏覽器互動、登入頁、按鈕、表單：瀏覽器能力。
- 明確圖片／影片／音訊：對應媒體能力。
- 明確排程、提醒、定期執行：排程能力。
- 明確「上次／之前／Discord 對話」：工作階段搜尋能力。
- 明確桌面點擊、視窗、應用程式：電腦操作能力。

同一訊息可能命中多個能力。任何否定、條件句或語意衝突使信心下降時，交由 AI 分類，不以規則強判。

### 4.4 AI 分類器

AI 分類器只能回傳預先定義的能力列舉與信心，不得回傳任意工具名稱或權限決策。建議能力列舉：

- `none`
- `web`
- `files_read`
- `files_write`
- `terminal`
- `browser`
- `vision`
- `media`
- `desktop`
- `history`
- `memory`
- `skills`
- `delegation`
- `schedule`
- `messaging`
- `planning`

輸出必須通過 JSON 結構驗證；未知能力、缺欄位、超時、連線錯誤或低信心都進入失效開放流程。分類器不接收工具完整結構，只接收短能力目錄與必要的使用者訊息，避免把省下的 Token 搬到路由模型。

## 5. 設定

新增設定：

```yaml
tools:
  tool_search:
    enabled: on
    defer_core: true
    always_visible:
      - clarify
      - skill_view
    search_default_limit: 5
    max_search_limit: 20
  tool_router:
    enabled: true
    mode: hybrid
    provider: rdchat-direct
    model: gemma4:e4b-64k
    timeout_seconds: 4
    confidence_threshold: 0.75
    max_candidates: 6
    max_packet_tokens: 1800
    include_compact_schemas: true
    fail_open: true
    telemetry: true
```

設定解析必須對錯誤值採安全預設；`defer_core` 預設為 `false`，確保上游既有使用者升級後不會無聲改變行為。本機設定在測試完成後才明確開啟。

## 6. 模組邊界

### 6.1 `tools/tool_search.py`

- 擴充 `ToolSearchConfig`：`defer_core`、`always_visible`。
- 將「平台核心工具」與「永遠可見工具」分離。
- `is_deferrable_tool_name` 必須接受已解析政策，且未知工具仍維持可見，防止靜默遺失。
- `scoped_deferrable_names`、搜尋、說明與呼叫必須使用相同政策。
- 保留橋接遞迴阻擋與工作階段範圍檢查。

### 6.2 `agent/tool_router.py`

新增獨立、可單元測試的模組：

- 設定解析與驗證。
- 高信心快速規則。
- 能力到工具名稱的映射。
- AI 分類呼叫與 JSON 驗證。
- 路由封包建立與 Token 上限裁切。
- 失效開放結果。
- 不直接執行任何工具。

### 6.3 對話迴圈整合

在新使用者訊息送入主模型前建立一次路由決策；同一個使用者回合內的工具往返沿用該路由封包，不重複呼叫分類器。若主模型使用 `tool_search` 補救，不重跑分類器。

CLI、Gateway、API Server 與其他共用 AIAgent 對話迴圈的入口都走同一整合點，避免各平台分叉。

### 6.4 設定與文件

- 在預設設定與設定參考加入新欄位。
- `defer_core` 預設關閉。
- 文件說明路由器只推薦工具、不能提升權限。
- 文件說明設定變更需要新工作階段或 Gateway 重啟。

## 7. 安全與範圍不變量

1. 路由候選只能取自當前工作階段預組裝工具清單。
2. `tool_call` 不能呼叫橋接器本身。
3. `tool_call` 不能呼叫未授權、可用性檢查失敗或不在本工作階段工具組的工具。
4. 所有間接呼叫仍走直接呼叫相同的核准、掛鉤、截斷與紀錄。
5. AI 分類器不能改設定、不能執行工具、不能批准命令。
6. 路由器失敗不等於取消安全檢查；只代表主模型可搜尋完整「已授權」目錄。
7. Webhook 等受限平台仍維持其原始安全工具集合，路由器不能擴張。
8. 子代理與 Kanban 工作者仍遵守現有隔離與範圍規則。

## 8. 錯誤處理

- 規則無法判斷：交 AI，不視為錯誤。
- AI 超時／無法連線／非 JSON／未知能力／低信心：產生 `fallback` 路由封包，允許搜尋全部已授權工具。
- 候選工具因環境漂移消失：忽略該候選並允許搜尋補救。
- 路由封包超過上限：先移除詳細說明，再移除精簡參數結構，最後縮減候選數；不得截斷成無效 JSON。
- 橋接搜尋無結果：回傳結構化錯誤與可搜尋能力提示，不猜測不存在的工具。
- 路由器自身例外不得中斷主對話。

## 9. 效能與觀測

每回合記錄不含使用者敏感內容的結構化指標：

- 路由模式與來源。
- 規則／AI／退回次數。
- 路由耗時。
- 候選工具數。
- 路由封包估計 Token。
- 原始全部工具結構估計 Token。
- 固定可見工具結構估計 Token。
- `tool_search` 補救次數。
- 找不到工具與越權拒絕次數。

預設只寫本機日誌，不寫入 durable memory 或觀智核。不得記錄 API 金鑰、OAuth、完整私人訊息或工具參數。

## 10. 測試策略

### 10.1 單元測試

- 設定預設、錯誤值、上下限與向後相容。
- `defer_core: false` 保持現有核心永不延遲行為。
- `defer_core: true` 時只有 `always_visible` 直接可見。
- 未知工具不被靜默延遲或丟失。
- 規則分類的正例、否定句、衝突與多能力。
- AI JSON 成功、低信心、錯誤格式、未知列舉、超時。
- 路由封包 Token 上限與有效 JSON。
- 路由候選不得超出工作階段工具組。

### 10.2 整合與安全回歸

- CLI 與 Gateway 使用相同決策模組。
- 直接呼叫與橋接呼叫觸發相同批准與掛鉤。
- 受限工具組不能搜尋或呼叫範圍外工具。
- Webhook 不會因路由器取得終端機／寫入能力。
- 子代理不能透過橋接器取得父層或 Kanban 權限。
- 路由器故障時主對話仍可使用完整已授權目錄。
- 既有 `tests/tools/test_tool_search.py` 的 OpenClaw 與工具組範圍回歸測試持續通過。

### 10.3 端到端情境

至少測試：

1. 純聊天：不呼叫 AI 分類、不載入候選工具結構。
2. 最新資訊：路由到網路能力。
3. 本機檔案讀取與修改：路由到檔案／終端機，寫入仍受原安全流程。
4. 程式測試與除錯：路由到檔案、終端機與程式碼執行。
5. 瀏覽器互動：路由到瀏覽器。
6. 排程工作：路由到排程。
7. Discord 歷史接續：路由到工作階段搜尋。
8. 模糊複合任務：觸發 rdchat-direct。
9. rdchat-direct 關閉或超時：失效開放且可完成任務。
10. 越權工具名稱：拒絕並保留審計紀錄。

## 11. 基準與成功標準

在修改前後以相同主模型、全新工作階段與固定測試語料比較：

- 主模型每次呼叫的工具結構估計 Token。
- 第一個主模型請求的輸入 Token 與快取 Token。
- 路由器額外耗時。
- 首次有效工具呼叫時間。
- 整體任務完成時間。
- 路由補救率與任務成功率。

第一版驗收條件：

- `defer_core: false` 時行為與現況相容。
- 啟用後，主模型固定可見工具結構顯著低於現況完整核心工具結構。
- 純聊天高信心案例不呼叫前置 AI。
- 模糊案例可由 rdchat-direct 回傳合法分類，故障時自動退回。
- 所有目標情境可完成，且範圍與批准回歸測試通過。
- 不出現未授權工具可搜尋、可說明或可呼叫的情況。
- Gateway 重啟後 Discord 使用同一功能；CLI 新工作階段亦使用同一功能。

## 12. 推出與回復

1. 先建立修改前基準。
2. 實作功能但保持 `defer_core: false`、`tool_router.enabled: false` 的上游安全預設。
3. 跑單元、整合、安全與端到端測試。
4. 在本機設定明確啟用。
5. 啟動新 CLI 工作階段驗證。
6. 從外部重啟 Gateway，再驗證 Discord。
7. 若發生回歸，關閉 `tools.tool_router.enabled` 與 `tools.tool_search.defer_core` 即可回復原完整工具行為，不需回退資料或刪除工作階段。

## 13. 實作順序

1. 建立基準腳本與現況量測。
2. 擴充工具延遲政策與回歸測試。
3. 實作路由設定、規則、AI 分類與路由封包。
4. 整合共用對話迴圈。
5. 增加觀測指標與文件。
6. 執行完整驗證與安全審查。
7. 明確修改本機設定並重啟驗證 CLI／Gateway。
